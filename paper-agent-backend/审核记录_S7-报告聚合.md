## 0. 本步开始前发现的真实缺口（先说结论）

按 §9.5 验收「Given 任务正常完成，When 请求报告，Then 返回完整结构化报告与 MD」，
在动手写接口前先核查了既有产物，**发现流水线从未生成 `report.json`**：

```
$ find runs -maxdepth 2 -name "report.json" | head
（无输出）
```

13 个历史 run 目录全部只有 `state.json / ledger.jsonl / draft.md / review.json`。
原因：`pipeline.run_all` 只跑 R1–R6，**没有任何一步调用 `report.assemble`**；
`sciret_report` 工具虽已注册，但 `buildInstruction` 未要求模型调用它。

因此"终态 DONE **且报告就绪**"（P-03 核心验收）此前**无法闭合**——即使把四个接口写出来，
`/report` 也永远返回 `generating`。这不是接口层问题，而是**内核流水线缺一环**。

处置：先补内核（`run_all` 收敛到 `DONE` 后自动装配报告，门禁不过则拒绝并留痕），再做 BFF 只读装配。
顺序不可颠倒——否则等于把"生成"偷偷搬进 BFF，违反「执行不绕过 AGH / 内核确定性」红线。

## 2. 本步修掉的一个真实安全缺口

审核中发现：内核能**检测**账本篡改并拒绝出报告，但**磁盘上残留的 `report.json` 不会被处理**。
后果：报告生成后再手工改账本，BFF 的 `/report` 只看「`report.json` 是否存在」，
会继续把**基于旧账本**的报告当作有效产物返回——正是 §11「篡改即拒绝出报告」要防的情形。

处置（`report._invalidate_existing`）：门禁不过时把 `report.json` / `report.md`
**改名**为 `*.invalid`（可逆、不删数据），使下游立即回到「未就绪」，同时把作废事实写进 `report_gate.json`。

实测：

```
$ sed -i 's/关键要素/被篡改要素/' ledger.jsonl && python -m sciret_kernel report ...
…账本校验失败[CHAIN_MISMATCH] seq=16 … 已作废残留产物：report.json.invalid, report.md.invalid

$ ls runs/run-m6e2e-110214
draft.md  ledger.jsonl  report.json.invalid  report.md.invalid  report_gate.json  review.json  state.json
```

恢复账本后报告可重建（可恢复性），一并验证通过。

## 5. 顺带修正的既有失败用例（审核发现，非本步引入）

`test_two_runs_produce_identical_digest` 在 **改动前的 HEAD 版本上就已失败**（用 `git stash` 对比确认）。
根因是用例自身缺陷：两次运行用了不同目录名 `run-a` / `run-b`，而 `task_id = 目录名`，
`task_id` 又进入 `state.json` 与报告正文 → **输入本就不同**，断言"摘要必须一致"不成立。

修正：两次用**不同物理目录**（`dir-one` / `dir-two`，证明不依赖路径）但**相同 task_id**（`run-fixed`），
并给 `plan()` 加 `task_id` 参数。这才是"相同输入 → 相同摘要"的正确表达。

顺带确认：M6 的报告生成**不引入非确定性**——两次同输入执行的 `ledger_digest` 一致，
报告复用逻辑以 `ledger_digest` 为键，未破坏可复现性（§10）。

### 5.1 追查后确认的另一个真实边界：墙钟时间戳进哈希链

修正用例后，测试一度**偶发失败**（跨秒边界）。追查结论：这不是测试问题，而是**真实的可复现性边界**——
账本记录的 `at`（秒级墙钟）**参与 `chain_hash` 与 `ledger_digest`**，
故两次相同输入的执行若跨秒，摘要必然不同。

处置遵循 §464「显式排除不可承诺项」的精神，**不掩盖、不假装能做到**：

1. 用 `freeze_clock()` 注入固定时间戳，验证「除墙钟时间戳外完全确定」这一可承诺的部分；
2. 另加一条用例**如实断言**"跨秒则摘要不同"，把边界固化为可执行的文档；
3. 在 README §8 写明该边界与**正确的修法**（若将来要整账本逐字节可复现，应引入
   `SOURCE_DATE_EPOCH` 式冻结参数，而非把时间戳从链里剔除——审计要求记录真实发生时间）。

排查中还暴露一个自己写的测试 bug：用 `stamp[-9:-7]` 推导目录名，对同一秒内的两个时间戳会切出**相同**目录名，
第二次运行便复用已有账本文件，产出"摘要相同"的假象。已改为显式索引命名，并在 README §8 记为通用坑位。
